# meta-publish

노션에서 카드뉴스를 검수한 뒤 컨텐츠 DB의 **`인스타그램 배포`·`스레드 배포` 버튼**을 누르면 해당 채널에 자동으로 발행하는 시스템이다.

## 구조

| 경로 | 설명 |
| --- | --- |
| `supabase/functions/meta-publish/index.ts` | 발행 함수 본체 |
| `supabase/functions/meta-publish/lib.ts` | 캡션·정렬·장수 검사 등 순수 로직 |
| `supabase/functions/meta-publish/lib_test.ts` | 순수 로직 테스트 |
| `supabase/meta_tokens.sql` | 스레드 토큰 보관 표 생성 SQL |
| `supabase/meta_jobs.sql` | 발행 잠금 표 생성 SQL (중복 게시 방지) |
| `.github/workflows/deploy-supabase-functions.yml` | 타입 검사·테스트 후 Supabase로 배포 |

## 동작

1. 노션 버튼이 ① 해당 채널의 상태를 **`⚪ 대기`로 바꾸고** ② 웹훅을 보낸다
2. 함수가 **즉시 202(접수)로 응답**하고, 실제 발행은 백그라운드에서 이어간다
3. 함수는 웹훅 본문에 실려 온 페이지(`data.id`)를 대상으로 잡는다. 페이지가 없으면 `⚪ 대기`로 남은 행을 조회하는 큐 모드로 넘어간다
4. 채널별로 잠금을 걸고(중복 게시 방지) 컷 이미지를 Supabase Storage 공개 버킷에 올린다 — 인스타그램은 공개 URL만 받기 때문
5. 해당 채널 상태를 `🔄 작업중` → `✅ 완료`(실패하면 `⚠️ 오류`)로 옮기고 게시물 링크를 기록한다
6. `처리 시작 시각`·`발행 시각`을 남기고, 실패가 없으면 `마지막 오류`를 비운다

노션 버튼 웹훅은 10초 안에 응답이 와야 한다. 발행은 그보다 오래 걸리기 때문에 접수 응답을 먼저 보내고 나머지를 백그라운드로 넘긴다. 그래서 **202는 접수일 뿐이고 성공이 아니다.** 실제 결과는 페이지의 `인스타그램 상태`·`스레드 상태`·`처리 시작 시각`·`마지막 오류`로 확인한다.

채널마다 작업이 분리되어 있어서 인스타그램과 스레드가 서로의 실패에 영향을 주지 않는다. 한 채널이 실패해도 다른 채널은 그대로 올라간다.

스레드 토큰은 60일짜리라 `meta_tokens` 표에 담아두고, 발행할 때마다 마지막 갱신 후 30일이 지났으면 먼저 자동으로 연장한다.

## 컨텐츠 DB 속성

| 속성 | 종류 | 쓰는 주체 |
| --- | --- | --- |
| `인스타그램 상태` · `스레드 상태` | 선택 | 버튼이 `⚪ 대기`, 함수가 `🔄 작업중` → `✅ 완료`/`⚠️ 오류`. 비어 있으면 요청 없음 |
| `실시간 처리 상태` | 수식 | 채널 상태를 모아 작업중·오류일 때만 메시지를 띄운다. 평소엔 빈 값 |
| `마지막 오류` | 텍스트 | 함수. 실패 사유를 남기고 성공하면 비운다 |
| `처리 시작 시각` | 날짜 | 함수. 상태가 `🔄 작업중`으로 바뀐 시점. 워치독이 이 값으로 멈춘 작업을 회수한다 |
| `발행 시각` | 날짜 | 함수. 한 채널이라도 성공하면 기록 |
| `인스타그램 링크` · `스레드 링크` | URL | 함수 |

채널 상태가 요청 표시와 진행 표시를 겸한다. 그래서 별도의 작업중 체크박스도, 전체 요약 `발행 상태` 도 쓰지 않는다. `발행 채널`·`결과` 속성도 삭제했다. 전체 요약은 `실시간 처리 상태` 수식이 채널 상태로 계산한다.

## 한 번만 준비하면 되는 것

### 1. 공개 저장소 버킷

Supabase 대시보드 → Storage → 새 버킷 `meta-publish`, Public bucket 켜기.

### 2. GitHub 저장소 시크릿

Settings → Secrets and variables → Actions

| 이름 | 값 |
| --- | --- |
| `SUPABASE_ACCESS_TOKEN` | Supabase 계정 액세스 토큰 |
| `SUPABASE_PROJECT_ID` | 배포 대상 프로젝트 ref |

### 4. 표 두 개

Supabase 대시보드 → SQL Editor 에서 아래 파일 내용을 붙여넣고 실행한다. service role 만 읽고 쓸 수 있다.

- `supabase/meta_tokens.sql` — 스레드 60일 토큰 보관
- `supabase/meta_jobs.sql` — 발행 잠금. 같은 행의 같은 채널을 두 실행이 동시에 처리해 같은 글이 두 번 올라가는 것을 막는다. 표가 없어도 함수는 잠금 없이 동작한다

### 5. 스레드 인증 (한 번만, 그리고 60일마다 한 번씩)

Threads API 는 페이스북 로그인으로 붙는 경로가 없어 스레드 자체 OAuth 를 한 번 거쳐야 한다.

1. 메타 앱 대시보드 → 이용 사례 → Threads API 액세스 → 설정 에서 **리디렉션 콜백 URL** 을 등록한다.
   `https://<프로젝트 ref>.supabase.co/functions/v1/meta-publish`
   입력 후 반드시 **Enter** 를 눌러 태그로 만들어야 저장된다.
2. 같은 화면에서 앱 역할에 `ha.da_2025` 를 Threads 테스터로 추가한다.
3. 브라우저에서 아래 주소를 열면 승인 링크가 나온다. 링크를 눌러 승인한다.

   ```
   https://<프로젝트 ref>.supabase.co/functions/v1/meta-publish?threads_auth=1
   ```

4. 승인하면 함수로 되돌아오고, 함수가 code 를 60일 토큰으로 바꿔 `meta_tokens` 표에 저장한 뒤 `스레드 인증 완료` 안내를 보여준다.

이후에는 발행할 때마다 토큰이 자동으로 연장된다. 60일 넘게 발행을 쉬어 토큰이 만료되면 3번을 다시 하면 된다.

### 6. 노션 버튼 두 개

컨텐츠(학원관리) DB → 속성에서 버튼 두 개를 만들고 각각 이렇게 설정한다.

**`인스타그램 배포`**

- 액션 1: 속성 수정 → `인스타그램 상태` = `⚪ 대기`
- 액션 2: 웹훅 전송
  - URL: `https://<프로젝트 ref>.supabase.co/functions/v1/meta-publish?channel=instagram`
  - 헤더: `x-admin-key: <ADMIN_SECRET 값>`
  - 본문: 속성 선택은 아무거나 (예: `이름`). 함수는 속성 값을 쓰지 않고 본문에 실려 온 페이지 ID 를 쓴다

**`스레드 배포`**

- 액션 1: 속성 수정 → `스레드 상태` = `⚪ 대기`
- 액션 2: 웹훅 전송 (URL 은 `?channel=threads`, 헤더는 위와 같다)

채널은 웹훅 URL 의 `?channel=` 로 정한다. 지정이 없으면 `⚪ 대기`·`🔄 작업중`인 채널을 처리 대상으로 본다.

노션 자동화 웹훅은 실행된 페이지를 통째로 실어 보낸다(`data` 안의 페이지 ID 와 속성). 그래서 버튼 Content 에 페이지 URL 을 넣지 않아도 되고, 어느 페이지를 대상으로 잡았는지 함수 로그의 `meta-publish 대상` 줄에서 확인할 수 있다. 페이지가 실려 오지 않으면 `⚪ 대기`로 남은 행을 줍는 큐 모드로 넘어간다.

## 수동 테스트

페이지를 지정하고 `?wait=1` 을 붙이면 접수 응답 대신 실제 결과를 돌려준다. `dryRun` 은 노션 읽기, 컷 정렬, 이미지 업로드, 캡션 조립까지만 하고 발행과 상태 변경은 하지 않는다.

```bash
curl -X POST "https://<프로젝트 ref>.supabase.co/functions/v1/meta-publish?wait=1&dryRun=true" \
  -H "x-admin-key: <ADMIN_SECRET 값>" \
  -H "Content-Type: application/json" \
  -d '{"pageUrl":"<컨텐츠 페이지 주소>"}'
```

큐 모드(웹훅이 페이지를 못 실어 왔을 때의 백업 경로)도 `?wait=1` 로 결과를 볼 수 있다. `⚪ 대기`로 남은 행을 전부 처리한다.

```bash
curl -X POST "https://<프로젝트 ref>.supabase.co/functions/v1/meta-publish?wait=1&dryRun=true" \
  -H "x-admin-key: <ADMIN_SECRET 값>" \
  -H "Content-Type: application/json" \
  -d '{}'
```

## 알아둘 제약

- 노션 버튼 웹훅은 10초 안에 응답이 와야 한다. 그래서 함수는 접수(202)만 돌려주고 실제 발행은 백그라운드에서 한다. **202를 성공으로 보면 안 된다.**
- 같은 행의 같은 채널을 두 실행이 동시에 처리하면 글이 두 번 올라간다. `meta_jobs` 표 잠금이 이를 막는다. 표가 없으면 잠금 없이 동작하므로 버튼을 연달아 누르지 않는다.
- 잠금이 15분 넘게 남아 있으면 다음 실행이 가져와 이어서 처리한다. 그래서 함수가 중간에 죽어도 작업이 영영 막히지 않는다.
- 채널 상태가 요청 표시를 겸한다. 함수가 끝까지 못 가면 `🔄 작업중`으로 남고, 그때는 `실시간 처리 상태`가 계속 `작업중`으로 보인다. 원인을 확인하고 상태를 직접 되돌린다. 15분이 지나면 워치독이 `⏱️ 타임아웃 복구`로 바꾸는 것이 2단계 예정이다.
- 한 번의 실행이 함수 실행 시간 한도를 넘지 않도록 110초를 넘기면 남은 행은 처리하지 않고 그대로 둔다. 응답의 `remaining` 에 남은 행이 담기고, 그때는 버튼을 한 번 더 누른다.
- 인스타그램 캐러셀은 2~10장, 스레드는 2~20장이다. 10장을 넘는 카드뉴스는 인스타그램에 올릴 수 없어 지금은 분할하지 않고 실패로 기록한다.
- 인스타그램은 이미지가 공개 URL이어야 한다. 노션 파일 링크는 만료되는 서명 URL이라 발행할 때마다 Storage에 다시 올린다.
- 노션은 업로드된 파일을 `binary/octet-stream` 으로 돌려주기도 한다. 그래서 content-type 을 믿지 않고 파일 앞바이트(PNG·JPEG·WebP·GIF)로 실제 형식을 판별한다.
- 영상 발행은 아직 지원하지 않는다. 이미지가 아니면 실패로 기록한다.
- 캡션은 채널별로 따로 검사한다. 인스타그램 2200자, 스레드 500자다. 두 채널 모두 쓰려면 해시태그 없이 고정 멘트를 포함해 500자 안으로 쓴다.
- 실패한 채널은 그 채널 버튼을 다시 누르면 된다. 성공한 채널은 상태가 `✅ 완료`라 다시 발행되지 않는다.
- 날짜 속성은 Notion REST 형식(`{"처리 시작 시각": {"date": {"start": "..."}}}`)으로 쓴다. 이 형식을 틀리면 페이지 속성 PATCH 가 통째로 거부된다.

## 검증 상태

- 통과: `deno check` 타입 검사, 순수 로직 테스트 19개
- 통과: 스레드 승인 화면 진입, 승인 code 수신까지 실제 앱으로 확인
- 통과: dryRun 으로 노션 읽기 → 컷 정렬 → Storage 업로드 → 캡션 조립까지 확인
- 확인: 버튼 웹훅 본문에 페이지 객체(`data.id` + 속성)가 실려 옴 (2026-10-08 실제 버튼 실행 로그)
- 미검증: 실제 발행, 앱 심사
- 고친 것: 날짜 속성 형식 오류로 발행 기록이 전혀 남지 않던 문제, 페이지가 실려 오면서 동기 실행으로 빠져 10초 제한에 걸리던 문제
